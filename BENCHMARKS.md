# Performance benchmarks

How to run the listview's performance benchmarks, compare two versions of the component, and read the results. The benchmarks answer three questions:

1. **Does a change make the listview faster or slower?** Run before and after, compare.
2. **Which of two implementations is faster?** Run each, compare.
3. **How fast is it?** Absolute numbers per list size, scenario and metric, for docs and design decisions.

They are maintainer tooling: not run in CI, no pass/fail thresholds, nothing shipped in the wheel.

## Quick start

From a clone with the frontend built (`npm ci && npm run build` in `streamlit_listview/frontend/`) and the dev environment installed (`uv run --extra devel playwright install chromium` once):

```sh
# Frontend tier: fast, React-only, relative numbers (~6 min for everything)
cd streamlit_listview/frontend
LISTVIEW_BENCH_SIZES=1000,50000 npm run bench

# Browser tier: real Chromium + Streamlit, numbers of record (~14 min for everything)
cd ../..
uv run --extra devel pytest e2e/perf/ --perf-out bench-results/quick.jsonl --perf-sizes 1000,50000 --perf-reps 1
uv run --extra devel python -m e2e.perf.report bench-results/quick.jsonl
```

PowerShell sets environment variables differently: `$env:LISTVIEW_BENCH_SIZES = "1000,50000"; npm run bench` (the variable then stays set for the session; clear it with `Remove-Item Env:LISTVIEW_BENCH_SIZES`).

## Test concept

### Where the benchmarks sit

| Layer | What it proves | Runs in CI | Gate |
|---|---|---|---|
| Python unit tests (`tests/`) | the wrapper's behaviour | yes | 100 % coverage |
| Frontend unit tests (`src/**/*.test.tsx`) | the React component's behaviour | yes | 100 % coverage |
| End-to-end tests (`e2e/`) | the component inside a real Streamlit app | no | pass/fail |
| Render budget (`e2e/test_performance.py`) | 5,000 rows render in under 15 s | no | a generous pass/fail budget against pathological regressions |
| **Performance benchmarks** (this document) | how fast, and whether a change helps | no | none: you read and compare numbers |

The benchmarks never fail because something got slower. They fail only when a scenario cannot run at all (a precondition does not hold, or a wait times out), so a broken measurement never passes as a fast one.

### Two tiers

| | Frontend tier | Browser tier |
|---|---|---|
| Runs in | `vitest bench` in Node, jsdom DOM, React development build | Playwright driving headless Chromium against a real Streamlit server |
| Measures | React's own work: reconciliation, memo recomputation, DOM mutation | everything a user waits for: Python call, payload transfer, parsing, React, style, layout, paint, scroll |
| Blind to | layout, paint, scroll, Streamlit's rerun round trip | nothing, but slower and noisier |
| Use it for | quick A/B of React-side changes, many samples per scenario | the numbers you quote; DOM-size or CSS work; anything Streamlit-side |
| Full matrix | about 6 min | about 14 min on the reference machine at 3 reps (15–20 min on slower machines) |
| Results | vitest table, JSON via `--outputJson`, built-in `--compare` | JSONL records, `python -m e2e.perf.report` |
| Code | `streamlit_listview/frontend/src/bench/` | `e2e/perf/` |

**Why two tiers.** The frontend tier isolates the part of the cost the component's own code controls, so a React-side improvement shows up at full size and with many samples. The browser tier adds everything around it. A fix can therefore look large in the frontend tier and smaller in the browser tier without being "broken": the browser tier also contains Streamlit's payload transfer and Chrome's work over a very large DOM, which React-side changes do not touch. Quote browser-tier numbers to users; use frontend-tier numbers to decide between code alternatives.

### The matrix

Every benchmark runs over the same cells:

- **Sizes:** 100, 1,000, 5,000, 10,000, 25,000 and 50,000 options. Around 50,000 is the practical ceiling of a non-virtualized list.
- **Shapes:** `grouped`, in groups of 100 with collapsible group headers, and `ungrouped`.
- **Dataset:** generated by `demo/data.py::make_large_dataset` (id `item-00042`, label `Item 00042`, group `Batch 000`). The frontend tier uses a TypeScript mirror (`src/bench/fixtures.ts`) that unit tests pin to the same literals as the Python generator, so both tiers measure identical rows.
- **Widget configuration:** single selection, search enabled, height 300 px, collapsible groups in the grouped shape. `add_option` additionally enables `accept_new_options`.

### Scenarios

| Scenario | What happens | What it exercises | Frontend | Browser |
|---|---|---|---|---|
| `mount` | render N rows from nothing until the last row exists | first render, DOM creation | render + unmount cycle | yes, timed from "show" |
| `rerun_unchanged` | the app reruns and sends identical options as fresh JSON | re-use of unchanged option objects, row memoisation | yes | yes, via an unrelated button |
| `rerun_one_changed` | the app reruns with one option's label changed | re-rendering exactly one row | yes | yes |
| `search_narrow` / `search_clear` | type a query matching one row, then clear it | filtering; re-inserting N−1 rows | merged as `search_narrow_then_clear` | separately |
| `click_select` | click an unselected row | selection state; in the browser also the round trip to Python | yes | yes |
| `group_collapse` / `group_expand` | toggle the first group header (grouped only) | removing and re-inserting 100 rows | merged as `group_collapse_then_expand` | separately |
| `add_option` | type a new value and press Enter, with one row selected | building the added row, the "already in the list?" lookup | yes | yes, on its own page load |
| `scroll` | 60 programmatic scroll steps through the list | frame time with the whole DOM | — | yes |

The frontend tier merges the two reset pairs because vitest's `bench()` has no per-iteration setup hook: every timed body has to leave the list ready for its own next iteration. The browser tier measures the halves separately.

### Design principles

- **Public surface only.** Both tiers drive the component through its props and DOM (frontend) or the `listview()` API and the rendered page (browser). They import no internal helper, so the same benchmark files run unchanged against any version of the component. That is what makes "main vs. my branch" possible.
- **Same machine, no stored baselines.** Absolute numbers depend on the machine, its load and its power settings. A comparison is always two runs on the same machine, close together in time. Results go to the gitignored `bench-results/`; baselines are never committed.
- **Fail loud, never time a no-op.** Every scenario checks a precondition before it is timed: the last row exists, the search needle matches exactly one row, the header really collapses the group, Enter really adds a row. In the browser tier, every wait has a 240 s timeout that raises. Unknown sizes or shapes in a filter are an error, never a silently smaller matrix.

## Methodology

### Frontend tier

- **Harness.** `vitest bench` (tinybench under the hood) in jsdom, rendering with `@testing-library/react`. One `describe` per cell (shape × size) and one `bench` per scenario.
- **Setup is untimed.** A bench's `setup` mounts the list, looks up the DOM elements the timed body needs, and checks the precondition. It runs once before the warm-up and once before the measured run; `teardown` unmounts and releases every cached handle, so 50k-row trees do not pile up in memory.
- **Self-resetting bodies.** `rerun_*` alternate between two pre-built fresh copies of the options, so every rerun hands the component new objects, the real rerun path, without building JSON inside the timed body. `click_select` alternates between two rows; `add_option` commits a new unique value each time.
- **Sample budgets.** Large cells would otherwise run for minutes:

  | Scenario group | ≤ 5,000 rows | 10,000 | 25,000 | 50,000 |
  |---|---|---|---|---|
  | `mount`, `search_narrow_then_clear` | tinybench default: ≥ 500 ms and ≥ 10 samples | 8 | 5 | 3 |
  | `rerun_*`, `click_select`, `group_collapse_then_expand` | tinybench default | 15 | 15 | 15 |
  | `add_option` | 10, fixed, because each added row stays in the list | 15 | 15 | 15 |

  A fixed count gets one warm-up iteration; the sub-second scenarios get two.
- **Positional pairing.** vitest's `--compare` matches benchmarks by their position in the file, not by name. The bench file therefore declares every cell and skips the ones a filter leaves out (`describe.skipIf`), so a subset run still lines up with a full baseline, as long as both sides use the same bench file.

### Browser tier

- **Harness.** A Streamlit app (`e2e/perf/app_bench.py`) is started once per pytest session. The cell is chosen by query string (`?n=…&grouped=…&newopt=…`). The list mounts only when the test clicks a "show" button, so the test times the mount itself. A "rerun" button causes an unrelated rerun; an "edit" button flips one option's label.
- **Fresh state per run.** Each measured run opens a new browser context (new Streamlit session, viewport 1280×900). One extra run per cell is discarded as a warm-up, then `--perf-reps` runs (default 3) are recorded, one JSON line each.
- **Timing inside the page.** Each scenario is a JavaScript snippet that starts `performance.now()`, performs the action, and waits frame by frame for the DOM condition: `rows_ms`. It then waits one animation frame plus a macrotask, so the browser has painted: `painted_ms`. Doing this in the page avoids a Playwright round trip per check, which at this scale would be the measurement.
- **Main-thread work.** Chrome DevTools Protocol `Performance.getMetrics` snapshots around a scenario give how long the main thread was busy: `task_ms`, split into `script_ms`, `recalcstyle_ms` and `layout_ms`. For `mount` the window opens only after the page has settled, so page loading is excluded.
- **Two end points for round trips.** `rerun_unchanged`, `rerun_one_changed` and `click_select` go through Python. `roundtrip_ms` ends when the app's status line shows the rerun. The component's re-render happens after that, so `settled_ms` also waits until the main thread has had no long task (≥ 50 ms, via `PerformanceObserver('longtask')`) for 300 ms, and ends at the end of the last one. Use `settled_ms` or `task_ms` to see the frontend's share.
- **Payload.** `ws_bytes` counts WebSocket bytes received during the mount and the unchanged rerun. `py_mount` records the Python call's duration (`py_ms`) and the options' JSON size (`options_bytes`). Streamlit resends the full options list on every rerun, and these fields make that visible.
- **CPU throttling.** `--perf-throttle 4` slows the CPU fourfold via `Emulation.setCPUThrottlingRate`, approximating a slow laptop. The default is 1 (none).
- **Which checkout is measured.** Streamlit registers a component's frontend files from the installed package when the server starts, and `python -m streamlit` puts the working directory first on the import path. The browser tier therefore always measures the checkout it is run from, and refuses to run from any other working directory. Each record is labelled with that checkout's `git describe`.

### A browser record

One line of the JSONL file, abbreviated:

| Key | Fields |
|---|---|
| `n`, `grouped`, `throttle`, `rep`, `branch`, `started` | metadata |
| `mount` | `rows_ms`, `painted_ms`, `task_ms`, `script_ms`, `recalcstyle_ms`, `layout_ms`, `ws_bytes` |
| `py_mount` | `py_ms`, `options_bytes` |
| `dom_nodes`, `heap_mb` | after the mount, after a forced GC |
| `search_narrow`, `search_clear` | `rows_ms`, `painted_ms` |
| `search_busy` | main-thread time over both search steps |
| `rerun_unchanged` | `roundtrip_ms`, `settled_ms`, `task_ms` and its parts, `ws_bytes` |
| `py_rerun` | `py_ms` |
| `rerun_one_changed` | `roundtrip_ms`, `settled_ms`, `task_ms` and its parts |
| `click_select` | `local_painted_ms` (the highlight before the round trip), `roundtrip_ms`, `settled_ms`, `task_ms` and its parts |
| `group_collapse`, `group_expand` | `rows_ms`, `painted_ms` (grouped only) |
| `scroll` | `p50_ms`, `p95_ms`, `max_ms` per frame |
| `add_option` | `rows_ms`, `painted_ms` |

## Prerequisites

- **Node 24** and the frontend dependencies: `npm ci` in `streamlit_listview/frontend/`.
- **A built bundle** for the browser tier: `npm run build` in `streamlit_listview/frontend/`. The benchmark stops with a message naming the missing directory if there is none.
- **uv** with the dev extra. Every Python command goes through `uv run --extra devel …`.
- **Chromium for Playwright**, once per machine: `uv run --extra devel playwright install chromium`.
- **Memory.** At 50,000 rows the jsdom worker peaks around 2.9 GB. On a smaller machine, run a subset.
- **A quiet machine.** Close heavy applications, keep the laptop plugged in, and never run two benchmarks at the same time.

## Running the frontend tier

Run from `streamlit_listview/frontend/`.

```sh
npm run bench                                                         # the full matrix, ~6 min
LISTVIEW_BENCH_SIZES=1000,50000 npm run bench                         # some sizes
LISTVIEW_BENCH_SHAPES=ungrouped npm run bench                         # one shape
npm run bench -- -t "rerun"                                           # only benchmarks whose name matches
npm run bench -- --outputJson ../../bench-results/before.json         # save the results
npm run bench -- --compare ../../bench-results/before.json            # compare with saved results
```

`LISTVIEW_BENCH_SIZES` accepts any of `100,1000,5000,10000,25000,50000`; `LISTVIEW_BENCH_SHAPES` accepts `grouped,ungrouped`. Anything else stops the run with an error naming the allowed values.

## Running the browser tier

Run from the repository root.

```sh
uv run --extra devel pytest e2e/perf/ --perf-out bench-results/run.jsonl                        # full matrix, 3 reps
uv run --extra devel pytest e2e/perf/ --perf-out bench-results/run.jsonl --perf-sizes 50000    # one size
uv run --extra devel pytest e2e/perf/ --perf-out bench-results/run.jsonl --perf-shapes grouped --perf-reps 5
uv run --extra devel pytest e2e/perf/ --perf-out bench-results/slow.jsonl --perf-throttle 4    # 4x slower CPU
```

| Option | Default | Meaning |
|---|---|---|
| `--perf-out FILE.jsonl` | none | where to append the records; without it the benchmark is skipped |
| `--perf-reps N` | 3 | measured runs per cell, after one discarded warm-up |
| `--perf-throttle RATE` | 1 | CPU slowdown factor via DevTools |
| `--perf-sizes LIST` | all | subset of `100,1000,5000,10000,25000,50000` |
| `--perf-shapes LIST` | all | subset of `grouped,ungrouped` |

Pass these options only with `e2e/perf/` on the command line. `pytest e2e/ --perf-out …` is an "unrecognized arguments" error; plain `pytest e2e/` collects the benchmark and skips it. `--perf-out` appends, so use a new file per run, or delete the old one first.

Summarise one run, or compare two:

```sh
uv run --extra devel python -m e2e.perf.report bench-results/run.jsonl
uv run --extra devel python -m e2e.perf.report bench-results/before.jsonl bench-results/after.jsonl --markdown > bench-results/before-vs-after.md
```

## Comparing two versions

### Before and after a change in the same checkout

```sh
# 1. before the change (the browser tier needs a bundle built from these sources)
(cd streamlit_listview/frontend && npm run build && npm run bench -- --outputJson ../../bench-results/before.json)
uv run --extra devel pytest e2e/perf/ --perf-out bench-results/before.jsonl

# 2. make the change; rebuild the bundle for the browser tier
(cd streamlit_listview/frontend && npm run build)

# 3. after the change
(cd streamlit_listview/frontend && npm run bench -- --outputJson ../../bench-results/after.json --compare ../../bench-results/before.json)
uv run --extra devel pytest e2e/perf/ --perf-out bench-results/after.jsonl
uv run --extra devel python -m e2e.perf.report bench-results/before.jsonl bench-results/after.jsonl --markdown
```

Use the same size and shape selection on both sides.

### Against another branch, for example `main`

Benchmark the other version in a worktree of its own, using **this checkout's** benchmark files, so both sides run identical scenarios:

```sh
HERE="$PWD"                                                     # this checkout's root
git worktree add --detach ../bench-baseline main
(cd ../bench-baseline/streamlit_listview/frontend && npm ci && npm run build)

# frontend tier
cp -r streamlit_listview/frontend/src/bench ../bench-baseline/streamlit_listview/frontend/src/
(cd ../bench-baseline/streamlit_listview/frontend && npx vitest bench --run --outputJson "$HERE/bench-results/main.json")
(cd streamlit_listview/frontend && npm run bench -- --outputJson ../../bench-results/branch.json --compare ../../bench-results/main.json)

# browser tier: run from the baseline's root, with the baseline's own uv environment
cp -r e2e/perf ../bench-baseline/e2e/
(cd ../bench-baseline && LISTVIEW_SKIP_NPM_BUILD=1 uv run --extra devel pytest e2e/perf/ --perf-out "$HERE/bench-results/main.jsonl")
uv run --extra devel pytest e2e/perf/ --perf-out bench-results/branch.jsonl
uv run --extra devel python -m e2e.perf.report bench-results/main.jsonl bench-results/branch.jsonl --markdown > bench-results/main-vs-branch.md

# clean up (--force: the copied files, node_modules and .venv are untracked)
git worktree remove --force ../bench-baseline
```

- **Why copy instead of pointing at the other checkout.** The browser tier always measures the checkout it runs from, and it refuses to run from anywhere else. The frontend tier imports the component relative to the bench file. Copying the benchmark files into the other checkout is the only way to measure its code with these scenarios.
- **Requirements for the other checkout.** It needs what the benchmark files import: `src/test/makeData.ts`, `demo/data.py::make_large_dataset`, the fixtures in `e2e/conftest.py`, and vitest 4. `main` has all of them as of October 2026. Much older versions may not.
- **Order.** Run the two sides one after the other, never in parallel, and keep the machine otherwise idle.

## Reading the results

### The frontend table

```
 ✓ src/bench/listview.bench.tsx > grouped n=50000 93551ms
     name                    hz       min       max      mean   …     rme  samples
   · rerun_unchanged     5.1684    160.84    325.88    193.48   …  ±15.28%       15  [3.55x] ⇑
     rerun_unchanged     1.4574    567.63    808.45    686.13   …   ±7.06%       15  (baseline)
```

- `mean` (ms) and `hz` (runs per second, 1000 / mean) are the headline. vitest prints no median in this table, but the JSON file has one.
- `rme` is the relative margin of error, the 95 % confidence half-width as a percentage of the mean. A difference smaller than the rme of either side is not a result.
- `samples` is the number of measured iterations; see the sample budgets above.
- With `--compare`, each benchmark gets a second line marked `(baseline)` and a ratio on the current line: `[3.55x] ⇑` means 3.55 times as many runs per second as the baseline, i.e. faster. `⇓` means slower.

### The browser report

```
n      shape      scenario      metric      median   low     high    reps
50000  ungrouped  search_clear  painted_ms  839      819     2,138   3
```

Comparing two files gives both medians, both ranges and the difference, `B − A`:

```
n      shape      scenario      metric      A median  A range        B median  B range      Δ       Δ %
50000  ungrouped  search_clear  painted_ms  3,838     3,827..3,873   839       819..2,138   -2,999  -78%
```

A negative `Δ` means B is faster. Rows that exist on one side only show `—`, and the footer counts them, for example the group scenarios when one side ran ungrouped only.

### Which metric answers which question

| Question | Look at |
|---|---|
| How long until the user sees the list? | `mount.painted_ms` |
| How long does typing a search, or clearing it, freeze the list? | `search_narrow.painted_ms`, `search_clear.painted_ms` |
| How expensive is a rerun of the app for this widget? | `rerun_unchanged.settled_ms` and `.task_ms`; `ws_bytes` for the payload |
| How quickly does a click show feedback? | `click_select.local_painted_ms`, and `settled_ms` for the full round trip |
| Does scrolling stay smooth? | `scroll.p95_ms` at 25k and 50k; 60 Hz is about 16.7 ms per frame |
| Is it the React side or the rest? | the frontend tier for the same scenario |

### Rules for drawing conclusions

1. **A difference inside the spread is not a result.** Frontend tier: compare the mean against its rme. Browser tier: compare medians, and check whether the two low..high ranges overlap.
2. **Check the canaries first.** `mount` and the search scenarios are stable and costly. If they moved between A and B by more than the change under test can explain, the machine was disturbed: repeat that cell before reading the cheaper scenarios. Transient load has slowed whole stretches of a run by 2 to 5 times.
3. **Compare like with like.** Same machine, same size and shape selection, same benchmark files, runs close together in time. The first cell of a run starts cold, which once made a 100-row mount read twice as slow in a subset run. Prefer full runs, or the same subset on both sides.
4. **Frontend numbers are relative.** jsdom is not a browser, and React runs its development build there. Use them to rank alternatives; quote browser numbers.
5. **Expect the browser tier to show a smaller gain for React-side fixes.** A rerun in the browser also contains the Python call (about 100 ms at 50k rows), the payload transfer (2.3 to 3.4 MB at 50k rows), parsing, and Chrome's style, layout and paint over about 200,000 DOM nodes. Only the React part shrinks.
6. **Small sizes are noisy and fast.** Below 5,000 rows most scenarios take a few milliseconds, and `scroll` sits at the 60 Hz frame time. Base decisions on 10k to 50k.
7. **Three reps detect large effects.** For a suspected 5 to 10 % effect in the browser tier, run that cell with `--perf-reps 10` on both sides.

## Worked example: `main` vs. the render-chunk branch

The first comparison, on 2026-10-03, measured `main` against a branch that re-uses unchanged option objects across reruns and renders rows in keyed chunks of 100. The machine was Windows 11 on a Core Ultra 7, at 1× CPU.

| Measurement | Rows | main | branch |
|---|---|---|---|
| Frontend: rerun, options unchanged, ungrouped (median) | 50k | 626 ms | 152 ms |
| Frontend: search narrow + clear, ungrouped (median) | 50k | 10.6 s | 1.9 s |
| Browser: clear the search, ungrouped (`painted_ms`) | 50k | 3.8 s | 0.84 s |
| Browser: rerun, options unchanged, ungrouped (`settled_ms`) | 50k | 492 ms | 276 ms |
| Browser: mount, all sizes (`painted_ms`) | | | 1 to 5 % slower, within noise |

How to read it:

- **The rerun fix** cut React's rerun work about fourfold in the frontend tier. In the browser it saved about 45 % at 50k ungrouped, because the payload transfer and Chrome's work over the full DOM remain. Rule 5 at work, not a contradiction.
- **The chunking fix** made clearing the search four to five times faster in both tiers. That cost was almost entirely React inserting rows.
- **Mount** was not a target and did not change.
- **One stretch of the first frontend run** came out 2 to 5 times slower, including 100-row cells the change cannot affect. Re-running those cells gave normal numbers. Rules 2 and 3 caught it.

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| `LISTVIEW_BENCH_SIZES: "2000" is not one of …` | a typo in the filter; use the listed values |
| `--perf-sizes: '2000' is not one of …` | the same for the browser tier |
| `pytest: error: unrecognized arguments: --perf-out` | the options exist only with `e2e/perf/` on the command line; run `pytest e2e/perf/ …` |
| all browser benchmarks show `SKIPPED` | `--perf-out` is missing |
| `no built bundle under …/frontend/build` | run `npm run build` in that checkout's `streamlit_listview/frontend/` |
| `run the browser benchmark from the root of the checkout it lives in …` | `cd` to the repository root that contains the `e2e/perf/` you are running |
| `benchmark precondition failed: …` | the component behaved differently than the scenario expects; the message names the condition. Investigate before weakening it |
| `benchmark timeout waiting for …` after 240 s | the page never reached the condition, for example a component that does not render every row |
| the frontend run dies with a heap or worker error at 50k | not enough memory; run a subset or close other applications |
| `UnicodeEncodeError` from the report | an old copy of `report.py`; the current one forces UTF-8 output |

**Known limitation: virtualization.** Both tiers consider a mount finished when the last row exists in the DOM. A virtualized (windowed) list never renders it, so the frontend tier fails its precondition and the browser tier times out. Benchmarking a virtualized implementation needs a different end condition for `mount`, for example the scroll height or a row-count attribute, first.

## Extending the benchmarks

**A new frontend scenario.** Add a `bench(...)` at the **end** of the cell's `describe` in `src/bench/listview.bench.tsx`. vitest pairs `--compare` by position, so inserting earlier shifts every later pairing. The pattern:

- `setup` mounts with the shared `mount()` helper, looks up the elements the body needs, and calls `precondition(...)` so the scenario cannot time a no-op.
- The body performs the timed operation and leaves the list ready for its own next iteration.
- `teardown: release` unmounts and clears the cached handles.
- Pick `budget(n)` for scenarios around a second or longer at 50k, `cheapBudget(n)` for faster ones.

Appending keeps every existing pairing, so saved frontend baselines stay comparable; the new scenario simply has no baseline yet. Any change to an existing scenario's body, setup or budget changes what it measures: re-record the baselines on both sides.

**A new browser scenario.** Add a JavaScript snippet to `e2e/perf/measure.py`, using `window.__bench` helpers such as `until`, `painted`, `byId` and `settled`, and call it from `run_cell`. The record key you write becomes the scenario name. `report.py` picks up any numeric field automatically.

**A new size or shape.** Extend `SIZES` / `SHAPES` in both `src/bench/fixtures.ts` and `e2e/perf/cells.py`, and adjust the sample budgets for anything larger than 50k.

**After any change to the benchmark code**, run the quick checks:

```sh
(cd streamlit_listview/frontend && npm run build && npm test)       # also typechecks the bench files
(cd streamlit_listview/frontend && LISTVIEW_BENCH_SIZES=100 npm run bench)
uv run --extra devel pytest e2e/perf/ -q                              # the report and helper unit tests
uv run --extra devel pytest e2e/perf/ -q --perf-out /tmp/smoke.jsonl --perf-sizes 100 --perf-reps 1
```
