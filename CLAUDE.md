# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`streamlit-listview` is a Streamlit **custom component** built on the **Components V2 API** (`st.components.v2.component`, Streamlit ≥ 1.51). Unlike the legacy v1 iframe API, a V2 component renders **inline** in the host page inside a **Shadow DOM** (`isolate_styles=True`), into which Streamlit's `--st-*` theme variables inherit. It is a selectable/scrollable list widget with single/multi selection, grouping, search, sorting, collapsible groups, `accept_new_options`, and Markdown labels/help.

The package is a **two-language project**: a thin Python wrapper (`streamlit_listview/`) and a React/TypeScript frontend (`streamlit_listview/frontend/`) compiled by Vite into a bundle the wrapper registers.

## Commands

The system `python` on `PATH` may not have this project's deps installed — **always go through `uv`**. Test/dev deps live in the `devel` extra, so `uv run pytest` fails; use `--extra devel`.

### Python tests (enforces 100% coverage)
```sh
uv run --extra devel pytest tests/                              # full unit suite
uv run --extra devel pytest tests/ --cov --cov-report=term-missing   # with coverage gate
uv run --extra devel pytest tests/test_listview.py::test_name  # a single test
```
Coverage is gated at `fail_under = 100` over `streamlit_listview` + `demo` (excluding `demo/app.py`, which is exercised by e2e). Keep it at 100%.

### Frontend tests (also 100% coverage, run from `streamlit_listview/frontend/`)
```sh
npm run build && npm test         # what CI runs — build FIRST, see below
npm test                          # vitest run with the 100% coverage gate + tsc typecheck
npx vitest run src/Listview.test.tsx   # a single test file
npm run coverage                  # the same vitest coverage gate, without the typecheck
npm run typecheck                 # tsc --noEmit only
npm run format                    # prettier
```
Vitest enforces 100% statements/branches/functions/lines, and `npm test` itself runs that coverage gate — so CI and the release job enforce it, not just a manually invoked `npm run coverage`. Unreachable defense-in-depth guards are marked with inline `/* v8 ignore */`. `src/bench/*.bench.tsx` (the performance benchmarks, see below) are excluded from the coverage run and from the production typecheck but are compiled by `npm test`'s `tsc -p tsconfig.test.json`; `src/bench/fixtures.ts` is ordinary covered source.

`npm test` **requires a built bundle**: `src/__tests__/single-file-build.test.ts` asserts on the gitignored `build/` directory (exactly one `index-*.js` + one `index-*.css`), so on a fresh clone it fails with `ENOENT ... scandir '.../frontend/build'`. Always `npm run build` first — it rimrafs `build/` up front, so the assertion can only ever describe the bundle compiled from the current sources.

### Performance benchmarks (NOT run in CI; no thresholds)
The full developer guide is `BENCHMARKS.md`; this section is the condensed version. Two tiers, both driving the component only through its public surface, so the same files benchmark any checkout — that is how `main` is compared against a branch. Sizes 100 / 1k / 5k / 10k / 25k / 50k; shapes `grouped` (batches of 100, the demo dataset) and `ungrouped`. Results go to the gitignored `bench-results/`; baselines are never committed, because the numbers are machine-specific and a comparison is always a same-machine pair. The only *gated* performance check stays `e2e/test_performance.py` (a generous 5k budget). **Reading a result:** a delta inside the spread is not a result. Browser tier: compare medians against the report's low..high range. Frontend tier: compare the mean (hz — vitest's table has no median, and `--compare` ratios hz) against its rme. Transient machine load slowed some 50k runs 2–3×, so when a cell's canaries (`mount`, the search scenarios) moved between the A and B runs by more than the change under test can explain, repeat that cell before reading the cheap scenarios. **Known limitation:** both tiers require the *last* row to exist after mounting (the frontend asserts it in every scenario's setup, the browser's `mount` waits for it), so a virtualized (windowed) implementation fails the first and times out the second — benchmarking one needs a different mount end condition.

**Frontend tier — vitest `bench` in jsdom** (`frontend/src/bench/`; run from `streamlit_listview/frontend/`). The everyday A/B instrument for React-side changes: reconciliation, memo recomputation, DOM mutation. Blind to layout, paint, scroll and Streamlit's rerun cost, and it runs React's *development* build in jsdom, so its numbers are relative — never quoted as user-facing timings.
```sh
npm run bench                                                                  # full matrix, ~6 min
LISTVIEW_BENCH_SIZES=1000,50000 LISTVIEW_BENCH_SHAPES=grouped npm run bench    # a subset; unknown values fail loudly
npm run bench -- --outputJson ../../bench-results/before.json                 # record a baseline
npm run bench -- --compare ../../bench-results/before.json                    # the working tree against it
```
Scenarios per cell: `mount` (a render + unmount cycle), `rerun_unchanged`, `rerun_one_changed`, `search_narrow_then_clear`, `click_select`, `group_collapse_then_expand` (grouped only), `add_option`. The two merged pairs exist because vitest's `bench()` passes tinybench no per-iteration hook — only a per-mode `setup`/`teardown` — so a body must leave the list ready for its own next iteration; the browser tier has the halves apart. **Sample budgets:** `mount` and `search_narrow_then_clear` use `budget(n)` (tinybench's default budget up to 5k rows, then 8 / 5 / 3 fixed iterations at 10k / 25k / 50k); the sub-second scenarios (`rerun_unchanged`, `rerun_one_changed`, `click_select`, `group_collapse_then_expand`) use `cheapBudget(n)` (15 fixed iterations above 5k) so small A/B effects resolve; `add_option` runs a fixed 10 up to 5k because every added option persists across iterations, and `cheapBudget`'s 15 above it. Even at 15 samples the 50k cheap scenarios show rme around 14%, so one run resolves effects of roughly that size, not 4–5%. At 50k the jsdom worker peaks around 2.9 GB RSS; on a machine with less memory run a subset with `LISTVIEW_BENCH_SIZES`. `*.bench.tsx` files are excluded from coverage and from the production typecheck but compiled by `npm test`'s `tsc -p tsconfig.test.json`, so they cannot rot unnoticed. **To benchmark another checkout** (a baseline): copy `src/bench/` into that checkout's `frontend/src/` (its `node_modules` installed), run `npx vitest bench --run --outputJson <file>` there — vitest's default benchmark glob already matches — then `--compare` here. **Subsets and `--compare`:** a subset (`LISTVIEW_BENCH_SIZES` / `LISTVIEW_BENCH_SHAPES`) still lines up with a full baseline: every cell is declared and skipped, never omitted, because vitest pairs `--compare` by position, not by name. Every cell renders with `collapsible_groups` on in the grouped shape, as the browser tier does, so a rerun never changes the configuration it mounted with.

**Browser tier — Playwright + pytest against a real Streamlit server** (`e2e/perf/`). The numbers of record, and the only tier that can judge DOM-size or CSS work: the 2026-10-03 spike found that after the identity and chunk fixes the remaining 50k rerun cost is Chrome's style/layout/paint over the whole DOM, not script. `perf`-marked and skipped unless `--perf-out` is given, so `pytest e2e/` is unchanged.
```sh
uv run --extra devel pytest e2e/perf/ --perf-out bench-results/branch.jsonl                     # full matrix, 3 reps, ~15–20 min
uv run --extra devel pytest e2e/perf/ --perf-out bench-results/quick.jsonl --perf-sizes 1000,50000 --perf-reps 1   # a quick look; --perf-shapes grouped|ungrouped narrows the shape
uv run --extra devel pytest e2e/perf/ --perf-out bench-results/slow.jsonl --perf-throttle 4      # CDP CPU throttling, the spike's slow-laptop column
uv run --extra devel python -m e2e.perf.report bench-results/branch.jsonl                        # medians per cell / scenario / metric
uv run --extra devel python -m e2e.perf.report bench-results/main.jsonl bench-results/branch.jsonl --markdown   # B against A
```
Per cell and rep (one warm-up rep is discarded; fixed waits cost ~10.5 s per measured run, plus ~0.3 s for each of its four `settled_ms` windows): `mount`, `search_narrow`, `search_clear`, `rerun_unchanged`, `rerun_one_changed`, `click_select`, `group_collapse` / `group_expand` (grouped), `scroll`, and `add_option` on a second page load with `accept_new_options=True`. Each reports wall time to its DOM condition (`rows_ms`) and to a painted frame (`painted_ms`); `mount`, the three scenarios that round-trip through Python and the search pair (as `search_busy`) add CDP main-thread durations (`task_ms`, `script_ms`, `layout_ms`, `recalcstyle_ms`). `mount`'s CDP fields and `ws_bytes` cover the mount alone — the window opens after the page has settled, right before "show" — and the cell records `dom_nodes`, `heap_mb` and `py_mount` (the Python call's `py_ms` and the payload's `options_bytes`: Streamlit resends the full options payload on every rerun, which `rerun_unchanged`'s `ws_bytes` shows). **Two end points on `rerun_unchanged`, `rerun_one_changed` and `click_select`:** `roundtrip_ms` ends when the status line shows the rerun; `settled_ms` ends once the main thread has been free of long tasks (≥ 50 ms, PerformanceObserver `longtask`) for 300 ms afterwards; `click_select` adds `local_painted_ms`, the local highlight before the round trip. The frontend re-renders *after* the status line, so use `settled_ms` (or `task_ms`) to see its cost; it only exceeds `roundtrip_ms` where such long tasks follow (large n, throttled CPU). `scroll`'s p50/p95 sit at the 60 Hz frame time below roughly 5k rows, so read scroll at large sizes. The report prints medians with low..high and the rep count; two files give a compare table (`A median`, `A range`, `B median`, `B range`, `Δ`, `Δ %`), and it forces UTF-8 stdout so `> file.md` works on Windows. **The browser tier measures the checkout it runs from** — Streamlit registers a V2 component's assets from the *installed* distribution when the server starts (`runtime.py` → `manifest_scanner`), before any script runs, so no switch inside the harness can point it at another checkout's bundle — and the server resolves the package from its working directory (`python -m streamlit run` puts it first on `sys.path`), so run from the checkout's root (enforced: the `perf` fixture stops, naming both paths, when the working directory is not the checkout the benchmark lives in; every record is labelled with that checkout's `git describe`). **To benchmark another checkout** (a baseline): build its bundle, copy `e2e/perf/` into it — the package is self-contained, its options and marker live in its own conftest — and from that checkout's root run `LISTVIEW_SKIP_NPM_BUILD=1 uv run --extra devel pytest e2e/perf/ --perf-out <absolute path>/bench-results/<label>.jsonl`; its own `uv` environment installs that checkout. The `--perf-*` options exist only when `e2e/perf` is on the command line: `pytest e2e/ --perf-out …` is an unrecognised-argument error, and plain `pytest e2e/` collects and skips the benchmark.

## Architecture

### Python wrapper (`streamlit_listview/`)
- `__init__.py` — declares the component at import time (`st.components.v2.component(..., js="index-*.js", css="index-*.css")`) and defines `listview(...)`. It **validates params** (`_validate_params`), normalizes options, resolves defaults, serializes a `data` dict to the frontend, and maps the returned selection ids back to the original Python objects.
- `_options.py` — `normalize_options` (id/label/group/disabled validation), `map_selection` (ids → original objects), `sort_items`. **id constraints:** ids must be *exactly* `str` or `int` — `float`, `bool` (an `int` subclass, so rejected explicitly), `None` and everything else are refused — an `int` id must satisfy `abs(id) <= 2**53 - 1`, and ids must be unique *as rendered*. All three rules come from the same place: the frontend keys rows by JavaScript `String(id)` and the payload crosses a JSON boundary, so ids that collapse to one string, spell differently in JS than in Python, or lose precision as doubles are rejected at the boundary rather than rendering ambiguously (or blanking the widget, when Streamlit's serializer swallows the `TypeError` for a non-JSON-serializable id). `_id_key` is the Python mirror of the frontend's `idKey` — `str()` agrees with JS `String()` for exactly the ids those constraints admit — and every Python question about *row* identity goes through it: the collision guard, `_resolve_default_ids`' membership check and de-duplication, and `map_selection`'s way-out resolution (Python `==` calls `"1"` and `1` distinct where the frontend renders and counts them as one row, so keying by equality let a `default` naming one row twice fail a `max_selections` the rendered selection satisfies, and let a selection be dropped as unknown while its row still rendered selected). **Don't write a second `str(id)` here** — same rule as `idKey` below. `_validate_id` is the shared per-id gate (str/int only, bool rejected, `abs(int) <= 2**53 - 1`), applied identically to option ids, `default` ids and the ids `_persisted_selection` reads back from `st.session_state[key]` — a default or persisted id is seeded straight into the frontend selection, so it crosses the same boundary (the persisted list degrades to `None` rather than raising, whole or not at all). `_resolve_default_ids` also ships each matched default in the **option's own spelling** (`default="1"` against the int option `1` ships `1`): the frontend canonicalizes its selection to the option's spelling on first render and commits any difference, so an un-canonicalized seed cost an extra rerun and a spurious `on_change` at mount.
- **`format_func` contract:** it maps an option → display label and receives **the option as passed** — the dict for dict options, the scalar itself for `str`/`int` options — so a label can be built from fields the option carries (`{"id": 1, "text": "Orders", "type": "Table"}` → `lambda o: ...`), which the id alone cannot reach. It is consulted only when an option has no usable `label`; an explicit `label` wins outright. **Which options actually reach it is the part people get wrong:** `{"label": None}` and `{"label": nan}` *carry* a `label` key and still route to the formatter, because `_is_usable_label` rejects them — and that is exactly the `df.to_dict("records")` NULL-cell shape, i.e. the most likely real-world dict population. A formatter written for plain values (`str.upper`, `LABELS.get`, anything `@lru_cache`d) therefore raises on those; the failure is wrapped as a `ValueError` naming the option. The default is `None`, not `str`: `str` would render a dict repr. `None` means "no formatter" and labels by `str(id)` — that literal `str(item_id)` in `_label_for` is *display*, deliberately **not** `_id_key` (see the row-identity rule above): they spell the same today, and routing it through `_id_key` would freeze the default label to the row-key spelling forever. The formatter gets the caller's own object, not a copy — `_label_for` runs *before* `group`/`disabled` are read off it, so a mutating formatter could change the rendered row; documented as read-only rather than defended against. `demo/data.py`'s presets each inline their own dict unwrap: `codegen` emits only `inspect.getsource(func)`, so a preset delegating to a shared helper would `NameError` in the snippet a user copies out. That is not licence to reproduce the label *precedence* rule demo-side — do not reintroduce a demo-side copy of the label rule. For the same reason the demo spots an *inert* preset (every option carries its own label, so nothing on screen changes) by counting the calls `listview` makes through `data.FormatProbe`, never by inspecting the options itself.
- `pyproject.toml` (nested, **shipped in the wheel**) — the component manifest Streamlit reads at runtime to resolve the asset globs (`asset_dir = "frontend/build"`). Its `name` must match the distribution name.

### Demo theme switcher (`demo/themes.py`)
The demo's **Theme** section overlays a `demo/.streamlit/config_theme_<name>.toml` onto Streamlit's live config, which shows the listview following a configured theme with no parameter of its own. The component needs nothing for this: `useColorScheme` and the inherited `--st-*` variables already track a live theme change. What is non-obvious:
- **It is process-global.** Streamlit has no per-session theme; every rerun builds the theme it sends from the global config. A switch therefore reaches *every* session on its next rerun, the hosted demo's other visitors included. That is accepted and labelled in the UI. It goes through the internal `streamlit.config.set_option` (the public `st.set_option` refuses theme options), and that call lives in `themes.py` only.
- **The picker mirrors `SERVER_THEME.active`, never session state.** `render_theme` writes the server's theme into the widget key before rendering, and only `on_change` switches. A picker driven by its own session state would show a stale pick, and re-applying it would undo another session's switch.
- **A switch reaches the browser one rerun late.** Streamlit sends a run's theme (`SCRIPT_STARTED`) before widget callbacks run, and `st.rerun()` inside a callback does nothing. So `_switch_theme` sets a flag and the top of `app.py` reruns. The 24 h expiry (`THEME_TTL`) is checked the same lazy way on each rerun; no timer thread, because nobody would see the theme change before their next rerun anyway.
- **Each switch restores the boot config first** (a snapshot of every `theme.*` option, taken at the first switch, so config.toml and CLI flags survive), so an option only the previous theme set never leaks into the next one.
- **"Streamlit default" is a string option, not `None`**: a selectbox renders a `None` value as an empty field (the same trap the Sort/Formatting pickers hit).
- **`LISTVIEW_DEMO_THEME_SWITCHER=0` (or `false`/`off`/`no`) switches the picker off per deployment**; unset means on, so local runs and the e2e suite need no setup. On Community Cloud it is a root-level secret, which Streamlit copies into `os.environ` at server start. Off, the Theme pill is filtered out in `render_demo` — `SECTIONS` itself stays a literal, because `tests/test_demo.py` reads it through the AST — `_switch_theme` refuses to switch, and `expire(enabled=False)` drops a still-applied theme on the next rerun. `_switch_theme` also ignores names outside `THEMES`: callbacks see the raw client value before the selectbox validates it. `e2e/demo/test_demo_theme_off.py` boots its own server with the variable set, through the conftest's `EXTRA_ENV`.
- **The files decide which themes exist; `config_themes.json` only names them.** `discover_themes` globs the `.toml` files, and `theme_labels` maps each `Name` to its `DisplayName` for the picker, so a file without an entry still shows up under its bare name.
- `tests/test_demo.py` pins every shipped theme file to real Streamlit option keys, because a typo there only logs a warning and drops the color. It also builds each theme the way Streamlit does, because a rejected value such as a Google Fonts URL naming two families raises on every rerun, and it checks that `config_themes.json` names exactly the shipped files. `e2e/demo/test_demo_theme.py` boots **its own** server (via `EXTRA_ENV`, which also pins the switcher on), because a theme left applied would leak into the other demo modules, which share one server.

### Frontend (`streamlit_listview/frontend/src/`)
- `index.tsx` — V2 `FrontendRenderer` entry; mounts one React root per component instance into the `.listview-root` scaffold (defined by the Python `html=`).
- `Listview.tsx` — the container component; composes hooks + presentational components.
- `components/` — `WidgetLabel`, `GroupHeader`, `ListItem`, `SearchField`, `SelectAllToggle`, `NewOptionInput`, `HelpTooltip`, `Markdown`.
- `hooks/` — `useSelection` (the one piece of state), `useFilter`, `useCollapse`, `useKeyboardNav`, `useScrollToItem`, `useColorScheme`.
- `utils/` — the shared, hook-free helpers. `ids.ts`: `idKey` (the single `String(id)` row identity every comparison funnels through), `itemIdByKey`, `disabledIdSet`. `text.ts`: `foldForMatch` (the ONE case/ß fold, shared by the search filter and the `accept_new_options` "already in the list?" lookup — two copies drift, and what the user can *find* would stop agreeing with what they can *add*) and `plainTextLabel` (the ONE Markdown-to-plain-text stripper, shared by the listbox's accessible name and the help trigger's "Help for &lt;label&gt;"; it reduces only the directives the renderer actually claims, taking that list from `BRACKETED_DIRECTIVES` in `markdown/streamlitPlugins.ts` — a name stripped here but left literal there would announce text the user cannot see). `container.ts`: `isInSidebar` (the ONE place that asks which Streamlit container this instance mounted into — see the sidebar-swap invariant below). `items.ts`: `reuseUnchangedItems`, which `Listview` runs `data.items` through on every render — every rerun ships the options as freshly parsed JSON, so without it a rerun of *any* widget in the app recomputed every memo keyed on the items and re-rendered every row (measured ~2 s main-thread per rerun at 50k rows on a 4×-throttled CPU). **Read the options through `Listview`'s `items`, never `data.items`.** **Look here before writing a second fold, a second stripper, a second `String(id)` or a second container probe.**
- `markdown/` — `streamlitPlugins.ts` + `Markdown.tsx`: a `react-markdown` stack matching Streamlit's own renderer (GFM + remark-directive for `:red[…]`, `:material/icon:`, `:streamlit:`, colors, badges; emoji statically imported, conditionally enabled). **No `unsafe_allow_html`** (raw HTML stays escaped); **LaTeX/KaTeX deliberately dropped** to keep the bundle small.
- `bench/` — the frontend-tier performance benchmark: `fixtures.ts` (the TypeScript mirror of `make_large_dataset`, pinned to the same literals as `tests/test_demo.py`; covered) and `listview.bench.tsx` (run by `vitest bench` only). Imports only `Listview`, the payload types and the shared `test/makeData` factory, so it benchmarks any checkout — see *Performance benchmarks* under Commands.

### Key invariants (read before touching these areas)

**Selection state lives on the frontend.** The selected ids are React state in `useSelection`, seeded at **mount only**: from `data.state_selection` — the persisted `st.session_state[key]` selection, which the wrapper ships for keyed instances (`_persisted_selection`, best-effort, `None` outside a runtime or when malformed) — when present, else from Python's `default=` (mirrored as `default_ids`; the committed value itself is the V2 `default={"selection": [...]}` mount state). The persisted channel exists because a keyed element id drops the container: moving the widget between `st.sidebar` and the main body remounts the frontend while the Python-side widget state survives, and a remount seeded from `default` rendered rows disagreeing with the value `listview()` kept returning. A later change to either field re-seeds neither the returned value nor the display — echoing a new `default` into the display would show a selection `listview()` does not return. Both are read-only input; the hook never writes them back as such.

Two things do write back through `setStateValue("selection", …)`: a user interaction, and a **reconciliation**. `useSelection` re-derives the rendered selection from the current payload during render (`reconcileSelection`) — dropping ids no longer in `items` (unless `accept_new_options`), collapsing duplicate row keys, canonicalizing an id that spells a row differently (`"7"` → the option's int `7`), and truncating past `max_selections` / past one in single mode — and commits the correction when it differs. That commit is indistinguishable from a click at the V2 layer, so **`on_change` fires once** on the rerun where a keyed caller shrinks `options`, lowers `max_selections` or flips `selection_mode`. That is deliberate: the alternative is a widget whose rows disagree with the value `listview()` returns. Do not "fix" it by suppressing the write-back, and do not reach for `setTriggerValue` — it is fire-and-forget, not persisted state. The write-back only lands on the *next* rerun, so `_options.map_selection` applies the same corrections on the way out (resolve each id by `_id_key` row identity to its original option, drop true unknowns, collapse duplicate row keys, truncate multi to `max_selections`) — same rules, same earliest-selected survivors, so the two can never disagree about what survives. Nothing arrives a rerun late anymore: a typed `"7"` that names the int option `7` maps back to that option on the same rerun, and the frontend's write-back merely confirms the canonical spelling.

Consequence: changing the `key` is still the only way to reset the widget — an unkeyed instance remounts (and resets) on *any* param change, a keyed one preserves UI state (collapse/search/scroll) and the selection. The demo (`demo/app.py`) folds `collapsed_groups`, `default`, and a reset nonce into `widget_key` for that reason. `collapsed_groups` seeds each group the **first time that group is seen** (`useCollapse`) — a group counts as seen only while `collapsible_groups=True` (its header is a toggle), so flipping the feature on later still seeds groups first sighted while it was off — which for the demo's always-present groups means mount, so a config change is inert on a keyed instance; and `default=` **never commits a value**, so a remount *without* persisted state — a `key` change — is the only way to make a new default the returned value. A remount that keeps the Python-side state (a keyed container move) re-seeds the selection from `state_selection` instead, though frontend-only UI state (collapse/search/scroll) still resets — it has no persistence channel.

**Single-chunk bundle.** Vite library mode with `cssCodeSplit: false` emits exactly one `index-[hash].js` and one `index-[hash].css`, which the Python `js=`/`css=` globs resolve to (zero or multiple files error at registration). **Do not introduce dynamic `import()`** — it splits a second chunk and breaks the glob. This is why `remark-emoji` is statically imported and KaTeX was removed.

**Rows render in keyed Fragment "render chunks" of 100** (`ROW_CHUNK_SIZE` in `Listview.tsx`; unrelated to the bundle chunk above). When one update brings thousands of new rows into a single parent — clearing the search, expanding a big group, options growing on a rerun — React's `getHostSibling` searches forward through every following new sibling once per row, O(k²): clearing the search over 50k ungrouped rows took ~7 s (~40 s on a 4×-slowed CPU), and ~0.85 s with the chunks (the same as the demo's 100-row groups). A row's chunk is its place in the **unfiltered** list ÷ 100 (`chunkOf`), never derived from the filtered rows: a filter then cannot move a row into another chunk, so narrowing keeps every survivor's DOM node, and returning rows land beside a settled survivor or in a wholly new chunk. Keying a chunk by its first *filtered* row instead remounted every survivor on scattered narrowing keystrokes (2–3× slower at 50k). The chunks are split inside the `renderBlocks` memo, not in the render. Being Fragments, they add no DOM — rows stay direct children of their block, which `scrollToId`'s sticky-header check and the `role="group"` structure rely on. Don't flatten them back into one `map`, don't derive the chunk from the filtered rows, and don't swap them for wrapper `div`s without updating both.

**Theming via `--st-*` only.** All CSS (`listview.css`) uses Streamlit's `--st-*` custom properties with fallbacks; no Bootstrap, no hardcoded palette. For light/dark-conditional styling, **do not use `prefers-color-scheme` or `light-dark()`** — the production bundler (lightningcss) rewrites them in ways that don't reach the shadow tree. Instead read the active Streamlit theme's `color-scheme` via `useColorScheme` (exposed as the `data-color-scheme` attribute on the root).

**The sidebar SWAPS the two background tokens.** Streamlit wraps the sidebar subtree in its own emotion `ThemeProvider`, and a V2 instance's `--st-*` block is generated from the theme context *at its own mount point* — so a sidebar listview inherits sidebar values with nothing plumbed through. Of the 63 `--st-*` properties only **`--st-background-color` and `--st-secondary-background-color` trade values** (light `#ffffff`/`#f0f2f6` ↔ `#f0f2f6`/`#ffffff`; dark `#0e1117`/`#262730` ↔ `#262730`/`#0e1117`); the heading font sizes/weights also shrink, and every other color — text, primary, border, the semantic palette — is byte-identical. Measured, not inferred: `--st-*` appears nowhere in Streamlit's source as a literal (it is built as `` `--st-${kebab(key)}` ``), so grepping for the names finds nothing and only a running app answers this. Consumed raw the swap **inverts the widget** in the sidebar — rows render on the group-header surface and headers on the row surface. Hence the `--listview-*` surface tokens, each named once on the container root: `--listview-surface` (frame, rows, pinned header) and its inset `--listview-inset-surface` (search and add-option fields) are the two raw tokens and are swapped together in the single `[data-in-sidebar="true"]` block, while `--listview-group-surface` is `--listview-bg-mix` — Streamlit's 50/50 mix of the two tokens, which is **symmetric, so the swap cannot move it** and it needs no sidebar override at all. A new painted surface picks up the correct sidebar behavior by referencing a token rather than by growing an override that can drift. Reference points if you retune them: **`st.selectbox` / `st.multiselect` / `st.text_input` fill their control from `--st-secondary-background-color` in BOTH containers**, and the open selectbox menu paints the app-level background in both — which is why "un-swap in the sidebar" is also "match Streamlit".

`data-in-sidebar` comes from `utils/container.ts::isInSidebar`, called in **`index.tsx`** — not from a `useColorScheme`-shaped hook. The renderer's `parentElement` *is* the open `ShadowRoot`, so the answer is available before the first render; an effect-based read lands a frame late and flashes the main-body colors on every mount (tolerable for the hover-only tooltip `useColorScheme` feeds, not for the list surface). It hops `ShadowRoot.host` first because **`closest()` does not cross a shadow boundary** — without the hop it answers null in the sidebar too, and the widget silently keeps the wrong colors rather than failing visibly. No observer: a keyed widget moving between containers remounts the frontend (see the selection-state invariant above), so this is a mount-time constant. The `[data-testid="stSidebar"]` hook is Streamlit-internal; the e2e suite already depends on it, and an upstream rename degrades to main-body colors rather than breaking.

Because the stylesheet is only ever *executed* in a browser, `src/__tests__/listview-css.test.ts` pins what the sheet says and **`e2e/test_sidebar_theme.py` and `e2e/test_native_parity.py` pin what a browser resolves it to** — comparing the widget against a real `st.selectbox`, `st.pills` or `st.text_input` rendered on the same page, never against a hardcoded hex. `test_native_parity_dark.py` re-collects the parity tests under `--theme.base dark`, the only boot that exercises the dark branch of the highlight formula below.

**A surface and its insets are declared as a pair.** A surface and anything painted *on* it must resolve to different `--st-*` tokens **in every scheme** — so a scheme that swaps one swaps both, and the two are declared together in one block rather than at their use sites. The help tooltip is the worked example (`--listview-popover-surface` / `--listview-popover-inset-surface`, both on `.listview-help-popover`, both re-declared by the dark override): the dark popover moved its ground to `--st-secondary-background-color` while the three surfaces rendered *on* it — the inline-code chip, the GFM table header, the fenced code block — stayed on that same token, so all three were painted the exact colour of their own ground and vanished. Light escaped only by accident, because the popover happens to sit on `--st-background-color` there; both containers were affected, so this one was **not** the sidebar swap above. A use site cannot see which ground its container resolved to in the current scheme, which is why the pair lives in one place and each scheme hands it the theme's two surfaces *swapped*. Keep each half literally *the other one of the two tokens* — not a fixed colour, not a `color-mix` off the ground — and the sidebar swap above then carries the pair for free: both halves invert together, so the popover contrasts in all four container×scheme combinations with no `[data-in-sidebar]` override. It is deliberately the one painted surface still reading the raw tokens, because it tracks Streamlit's own tooltip rather than the widget's list surface; if that ever has to change it becomes an entry in the `--listview-surface` family, never a raw spelling. `--st-code-background-color` looks like the obvious source for the code surfaces and is not — Streamlit derives it as a 50% mix of the two surfaces, so in light it lands a hair off `--st-background-color` and the chip all but disappears. Two more cases the same rule covers: the popover's inline-code rule is popover-scoped because the base chip rule is shared with the inline **label** tier, and that tier renders only in `WidgetLabel`, which paints no background and so sits on the host container's own — where `--st-secondary-background-color` is again the other token and contrasts in both containers for free; and `th` is an inset that is also a *container*, so a chip inside a table header reads the **ground** half, or it is painted the colour of the cell under it. `src/__tests__/listview-css.test.ts` pins all of it — that the halves differ in each scheme, that the dark block swaps them rather than re-pointing one, that every inset reads the token, and the source-order tie the `th` rule depends on. The list has a pair of the same shape: `--listview-surface` / `--listview-inset-surface`, where the swap comes from the **container** rather than the scheme, so it is the `[data-in-sidebar]` block that hands the halves the two tokens the other way round (pinned the same way, by "the halves differ and the sidebar swaps them").

**Every painted state mirrors the native widget that plays its part.** The list is an always-open `st.selectbox` menu, so each state is copied from a measured Streamlit reference (Streamlit 1.60, both themes), not invented: the **list surface** is the open menu's; the **row hover** is the menu's option highlight `darkenedBgMix15`, reproduced from Streamlit's theme source (`getColors`: bgMix with its HSL lightness −30 in a light theme, **+60 in a dark one**, at 15% alpha); the **selected row** is an active `st.pills` (primary at 10%, primary text — the tint `st.dataframe` gives a selected row); the **group band** is the `st.dataframe` header (bgMix); the **search field** is `st.text_input` (filled, its 1px border in its own fill, 1px primary on focus, no ring); and the **frame** turns primary for *focus only* — measured, no native input changes its frame on hover or wheel scroll, so do not add a hover border. Rules that follow from it:
- The highlight is a **pill painted by `.listview-item::before`** (the menu's geometry: 5px side inset = `sizes.tagMarginInsideBorder`, `0.375rem` radius = `radii.md2`, a fixed value in Streamlit, not derived from `--st-base-radius`). It sits at `z-index: -1`, which only stays inside the row because the row is `position: relative; isolation: isolate` — drop the isolation and every highlight silently disappears behind the list surface. The row box itself is never tinted.
- The highlight formula needs **relative colour syntax** (`hsl(from var(--listview-bg-mix) h s calc(l - 30))`), the only way to take an HSL step off a `var()`. Unlike `light-dark()`, lightningcss passes it, the `@supports not (…)` fallback and `:not(a, b)` through unchanged — verified in the production build; re-check `build/index-*.css` if the toolchain moves. Engines without it (or with the pre-2024 percentage form, Safari < 18) would invalidate the whole custom property at computed-value time, which no `var()` fallback catches; the `@supports not` block substitutes a faint text-colour mix. The dark branch is keyed on `data-color-scheme`, which `useColorScheme` sets a frame after mount — harmless for a hover-only colour, but do not key a mount-visible surface on it.
- The row **focus ring** (Streamlit's `focusRing`, primary at 50%) is drawn only under `.listview-listbox:focus-visible`: a mouse click moves the active descendant too (`onItemClick` → `setFocusToId`), and a ring on every clicked row is something no native menu shows. The listbox's own UA outline is suppressed for the same reason (the frame already turns primary on focus-within).
- The **seam under a pinned header** (`pin_search` or `select_all`) is painted by `.listview-header::after` as a background, and the body drops its top border under a header. Focus recolours the *borders* of header and body, so a seam that is a border either lights up (a primary line through the middle of the control) or, with only its colour reset, notches the outline where it meets the primary side borders. Keep the seam a non-border.
- A click on the frame's **empty space** — below the last row of a list shorter than `height` — is forwarded to the listbox (`onBodyClick` in `Listview.tsx`). Only a click whose target is `.listview-body` *itself*: rows, the search field and the add-option row are children that focus their own target, and forwarding every bubbled click would pull the caret out of an input. It is `onClick`, not `onMousedown`: focusing during mousedown loses to the browser's own mousedown focus handling unless the default is prevented, and preventing it on the scroll container risks the scrollbar.

**Build output is gitignored.** `streamlit_listview/frontend/build/` is generated and not tracked. A `git reset` never updates it. After editing anything under `frontend/src/`, you must `npm run build` and restart Streamlit for the change to appear in a running app. The `_build_backend.py` (in-tree PEP 517 backend) runs `npm run build` automatically during wheel/sdist/editable builds and fails loudly if the bundle is missing.

## CI (`.github/workflows/ci.yml`)
Node 24 → `npm ci` → `npm run build` → `npm test` (vitest with the 100% coverage gate + typecheck) → uv editable install with `LISTVIEW_SKIP_NPM_BUILD=1` → `pytest tests/` with the 100% coverage gate → build a wheel from a *clean* bundle (exercises the build backend) → `scripts/verify_wheel.py` confirms the wheel ships exactly one `index-*.js`/`index-*.css` and nothing else under `frontend/build/` (the registration contract) plus the manifest and license files. The e2e suite is intentionally not run in CI. Third-party actions are referenced by version tag (floating major tags such as `@v7` where the vendor publishes them); SHA pinning was dropped deliberately as unnecessary for this project. `astral-sh/setup-uv` rides a full version tag because it stopped publishing floating tags after v7, and it must stay **≥ v6**: v5 ran its own `uv venv` whenever `python-version` was set, so the explicit `uv venv` step fails on current uv ("A virtual environment already exists"). Don't set `activate-environment: true` without dropping that step, or the same clash comes back.

The build-before-test order is **load-bearing**, not cosmetic: `npm test` asserts on `build/` (see *Frontend tests* above), so testing first fails on a fresh `actions/checkout`. Building first means typecheck runs twice — harmless.

## Releasing to PyPI (`.github/workflows/release.yml`)
Releases publish via **PyPI Trusted Publishing (OIDC)** — no API tokens live in the repo. The workflow fires on a `v*.*.*` tag push and runs three jobs: **build** (tag↔`[project].version` guard → frontend build → frontend tests, in that order — see the CI note above → editable install as in CI → unit tests → `uv build` sdist+wheel with `LISTVIEW_SKIP_NPM_BUILD=1`, so the tested bundle is the packaged one → `verify_wheel.py` → `uvx twine check --strict`), **publish-to-pypi** (the `pypi` environment + `id-token: write` → `pypa/gh-action-pypi-publish`, which also uploads PEP 740 attestations), and **github-release** (Sigstore-signs the dists and creates the GitHub Release with `--generate-notes`, adding `--prerelease` for an `a`/`b`/`rc` tag). Actions are referenced by version tag, as in CI; `pypa/gh-action-pypi-publish` rides its vendor-advanced `release/v1` branch (pypa ships fixes by moving that branch), and `sigstore/gh-action-sigstore-python` uses a full version tag because the project publishes no floating major tag. With `astral-sh/setup-uv` ≥ v10 the default `enable-cache: auto` skips the uv cache on tag pushes, so the release build installs cold — intended, not a regression.

To cut a release, bump the version in **all five places that assert it** — the release job runs the unit suite and `verify_wheel.py` before publishing, so missing any one hard-fails the release:

1. `[project].version` in the root `pyproject.toml` — the source of truth: the workflow's tag guard and `verify_wheel.py`'s wheel-filename check compare against it.
2. `[project].version` in the nested `streamlit_listview/pyproject.toml` — `tests/test_packaging.py::test_versions_agree` pins it to the root.
3. `EXPECTED_VERSION` in `tests/test_packaging.py` — `test_root_version_is_target` / `test_nested_version_is_target` compare both pyprojects against it.
4. `README.md` — the wheel/sdist filename examples: `tests/test_readme.py::test_version_matches_pyproject_and_no_stale_scaffold` pins them to the root `pyproject.toml`. The version badge needs no bump — it is the live shields.io PyPI badge, so the test pins only the project name it queries.
5. `demo/requirements.txt` — the `streamlit-listview==<version>` pin the Streamlit Community Cloud demo installs (and so does the Codespaces dev container, `.devcontainer/devcontainer.json`, which Community Cloud generated and which runs `demo/app.py` the same way): `tests/test_packaging.py::test_demo_requirements_pin_the_released_version` pins it to the root `pyproject.toml`. The file sits next to `demo/app.py` so Community Cloud picks it before the root `uv.lock` (which would build the repo and needs npm, absent there). Community Cloud redeploys on every branch push, so push the **tag first** and the branch only once the publish job has finished — otherwise the hosted demo installs a pin PyPI does not have yet and fails until you reboot it.

Two more steps no test enforces: run `uv lock` so `uv.lock` records the new project version (otherwise the next `uv run` rewrites it as an unrelated diff), and turn the `Unreleased` heading in `CHANGELOG.md` into the version and release date.

Then commit, `git tag v<version>`, and push the tag to the **GitHub** remote by name (`git push <github-remote> v<version>`): the workflow only runs there, and a bare `git push --tags` goes to the default remote, which need not be GitHub. The build job hard-fails if the tag doesn't match `[project].version`, so the tag and the published wheel can never disagree.

**Pre-releases** use PEP 440's canonical spelling — `1.0.0rc1` (or `a1`/`b1`), tagged `v1.0.0rc1` — in all five places. Never `1.0.0-rc.1` or `1.0.0-preRelease`: the latter is not a valid version at all, and the former is normalized to `1.0.0rc1` in the wheel filename while the tag guard and `verify_wheel.py` compare the raw string, so the release fails. PyPI never lets a version number be reused (not even after deleting it), so a broken rc is followed by `rc2`, not re-uploaded. `pip install streamlit-listview` skips pre-releases; the `==1.0.0rc1` pin in `demo/requirements.txt` names one explicitly, so the hosted demo can run on the rc.

**One-time setup (must be done once before the first release, by a maintainer with PyPI access):**
1. On PyPI → *Account settings → Publishing*, add a **Trusted Publisher**: owner/repo of this GitHub repo, workflow filename `release.yml`, environment name `pypi`. For the very first publish the project won't exist yet — use the **pending publisher** form (same fields plus the project name `streamlit-listview`).
2. In the GitHub repo → *Settings → Environments*, create an environment named **`pypi`** (optionally add required reviewers / a tag protection rule as a release gate).

The package is pure-`py3-none-any` (the React bundle is data, not a compiled extension), so a single wheel + sdist covers every platform — no `cibuildwheel` matrix. The sdist ships the prebuilt `frontend/build/` and omits `frontend/src/`, so installing from sdist needs **no Node**.

## Docs
`README.md` documents the public API; `demo/README.md` covers the playground; `CHANGELOG.md` records user-visible changes per release (Keep a Changelog format); `BENCHMARKS.md` is the developer guide to the performance benchmarks (test concept, methodology, how to run, compare and read them). Keep it in step with the *Performance benchmarks* section above when either tier changes.

**Writing rule: every technical document in this repository (`README.md`, `demo/README.md`, `CHANGELOG.md`, `BENCHMARKS.md`, this file) follows plain English according to Strunk & White, *The Elements of Style*.** In practice: short sentences with one idea each; the active voice; statements in positive form (say what the code does, not what it no longer does); definite, concrete words and the measured number rather than "fast" or "large"; omit needless words and qualifiers ("very", "really", "simply"); parallel form for coordinate items (table columns, bullet lists, the halves of a comparison); no colloquialisms or metaphors the reader must decode ("under the hood", "canaries" without a gloss); jargon defined for the document's audience — a changelog reader is a Python user, not a React developer. Why: these files are read by users and by coding agents in every session, so a sentence that has to be read twice costs everyone, and a vague one leads to a wrong change. Review a draft against this rule before committing it, as `BENCHMARKS.md` and `CHANGELOG.md` were on 2026-10-04.

### README demo GIF (`assets/listview-demo.gif`)
**Regenerate the GIF in the same commit as any change to how the widget looks or behaves.** The README links the GIF at `HEAD`, so GitHub and the PyPI project page always show the copy on the default branch; a style change merged without it advertises a widget the code no longer renders. The rule covers `listview.css`, the markup in `Listview.tsx` and `components/`, the Markdown renderer, any hook whose effect the user sees (search, selection, select-all, collapse, keyboard focus), a Python default that changes rendering, and `scripts/gif/` itself. A refactor, a performance change or a test change needs no new GIF. When in doubt, regenerate: on one machine the generator is deterministic, so an unchanged widget yields a byte-identical file and no diff (verified on 2026-10-04: a fresh bundle at `cd78de0` reproduced the committed GIF exactly).

From the repo root, after a one-time `uv run --extra devel playwright install chromium`:
```sh
npm --prefix streamlit_listview/frontend run build
LISTVIEW_SKIP_NPM_BUILD=1 uv run --extra devel --with pillow python scripts/gif/generate.py   # -> assets/listview-demo.gif
```
- **Build first.** The generator captures the gitignored bundle in `frontend/build/`, and a source edit does not update it (see *Build output is gitignored*). A stale bundle yields a GIF of the old widget.
- **`--with pillow`** adds the one capture dependency the `devel` extra lacks.
- **Check the result before committing.** `--keep-frames` keeps the PNG frames under `build/gif-frames/`; open them and confirm the change shows.
- **Commit only a real change.** If the GIF changes although nothing visible did (another machine's fonts, a newer Chromium), leave it out of the commit.
- **Keep the capture working.** `scripts/gif/capture.py` finds the widget by its `data-testid`s (`stListviewOption-<id>`, `stListviewSearch`, `stListviewSearchClear`, `stListviewSelectAllToggle`, `stListviewGroup`). A renamed testid or a removed feature breaks it; fix the script in the same change rather than drop a step.

`scripts/gif/README.md` describes the generator's parts and options.
